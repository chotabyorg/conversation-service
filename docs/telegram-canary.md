# Goal4B Telegram managed path

## Design

- **Cohort and trusted binding.** The gateway keeps an exact sticky integration-to-agent map and a separately enabled new-admission cohort. Conversation keeps trusted `{owner_id, integration_id, agent_id}` bindings and its own new-admission cohort. Both default empty/disabled. The cohort must be a subset of sticky bindings. Rollback empties/disables only the new cohort; sticky bindings remain so a replay can be resolved by Conversation. An integration ID with a different Control Plane agent binding fails closed.
- **Trusted routing identity.** The gateway obtains `owner_id`, `integration_id`, and `agent_id` only from the authenticated Control Plane polling result. It compares the result with its configured binding and sends that identity through a scoped Conversation service principal. Telegram payload fields never select an owner, integration, or agent.
- **Provider scope.** Initial managed scope is text in a private chat with a non-anonymous sender and a positive Telegram `message_id`. The provider thread is the decimal `chat.id`; the canonical Conversation remains the Foundation tuple `(owner_id, integration_id, TELEGRAM, provider_thread_id)`. Groups, anonymous posts, non-text messages, and unusable message IDs keep the existing legacy behavior.
- **Provider event key.** The key is `b{bot_id}c{chat.id}m{message_id}` within the trusted integration scope. `update_id`, `from_user.id`, and text are in the immutable payload fingerprint; `update_id` is not treated as a clock or sequence. Text is excluded from the key, so changed text for the same provider message conflicts while a distinct provider message with identical text remains distinct.
- **Admission and canonical history.** A Conversation-owned Telegram admission transaction freezes `MANAGED` or `LEGACY`. A new MANAGED admission atomically records its event, canonical CUSTOMER Message, and admission identity before it becomes visible to the worker. LEGACY records routing identity only. Existing route wins on replay. The immediate Conversation worker creates/claims the stable AgentTurn and executes the existing ManagedTurn contract; the gateway only asks for admission, polls retained results, and performs provider I/O.
- **Replay and rollback.** Same identity plus same immutable payload returns the stored admission and canonical IDs; changed immutable payload fails closed. On rollback, new events in the sticky map request LEGACY, while an event already admitted MANAGED still returns MANAGED and follows retained execution/delivery evidence. Empty sticky configuration has no eligible new admissions; previously used sticky bindings must remain configured while their retained admissions may be replayed.
- **Outbound evidence and formatting.** The gateway retains the existing Telegram HTML formatter for managed drafts. Each provider send has a durable Conversation intent before `sendMessage`; successful responses retain the returned Telegram `message_id`; an explicit Bot API rejection is `FAILED`; transport uncertainty or an unfinished intent is `UNKNOWN`. An event with prior delivery evidence is never blindly resent. No READ/DELIVERED acknowledgement is inferred beyond a successful `sendMessage` response.
- **Scheduling boundary.** Goal4B's immediate path admits and processes each eligible message through its narrow Conversation-owned worker. The stacked Goal5 source adds an optional shared Conversation scheduler and dispatch fence; no policy is active by default, so Goal4B's immediate path remains the compatibility behavior until Goal5 is reviewed and separately activated. Goal5 adds no Telegram queue/session authority or gateway debounce.

## Compatibility boundaries

ManagedTurn request/result contracts, AI and Business behavior, Website admission/worker behavior, and non-cohort Telegram `/v1/chat/completions` behavior remain unchanged. No GitOps or production activation is part of this source/local checkpoint.
